# Claims and reads select nodes by one filter, across every project

## Approach

Build the persisted rotation cursor: a small `claim_cursors` table keyed by
`(org_id, principal_id, filter_hash)` that `ClaimNext` advances on every
successful claim and `Ready` reads without mutating, so both present nodes
in the same round-robin-across-projects turn order. The alternative
considered was deriving "whose turn" from the existing `leases` table (no
new schema, group ready projects by the principal's most-recently-claimed
project) — rejected because leases don't record which filter selected them,
so two independently-rotating claim loops by the same principal with
different filters (the exact case the work order calls out: `"'these two
projects' cannot be said at all"` today) would collapse into one shared
history. That's not a smaller version of the same feature, it's a different,
weaker feature that happens to pass the two-project acceptance test by
coincidence of tie-breaking. The cursor is the smallest structure that
actually satisfies "rotating per principal and filter."

The other load-bearing decision: round-robin selection is implemented as
"pick which project to draw from next" (a small, unlocked, non-ordered
query over `DISTINCT project_id`), and then reuse the *existing*
single-project `lockNextReady` — unchanged — to lock and take the top node
of that one project. This avoids rewriting `ReadyQuery.sql` into a
windowed, multi-project query, which Postgres forbids combining with
`FOR UPDATE` at the same query level. `Ready`'s presentation reuses the same
per-project ordered query (already exists, already tested) once per
eligible project and interleaves the pages in Go, rather than trying to
express the interleave in SQL. Every project.org boundary here is already
`org_id`-scoped everywhere in the store, and there is no per-project ACL
(`internal/domain/project.go`, `internal/server/graph.go`), so "every
project the principal can read" is simply "every project of the caller's
org" — no new authorization plumbing is needed for the org-wide default.

1. **Proto: `NodeFilter`, and the mechanical rewire.**

   (`projects`, `kinds`, `labels`, `any_labels`, `assignee_kind`,
   `min_priority`, `parent`, `status`, `held`); `ClaimNextRequest`,
   `ReadyRequest`, `ListNodesRequest` drop their own filter fields and
   `project` for `filter NodeFilter`. Regenerate (`make generate`). Update
   every Go call site that fails to compile: `internal/domain/ready.go`
   (`ReadyQuery` gains `Kinds []string`, `AnyLabels []string`, `Parent
   string`, replacing singular `Kind`), `internal/domain/nodes.go`
   (`NodeListQuery` gets the same plus drops the single-project
   requirement — `ListNodes` becomes `project_id = ANY($n)` when `Projects`
   is non-empty, no predicate when empty), `internal/domain/lease.go`
   (`ClaimRequest` gets `Projects []string`, `Kinds`, `AnyLabels`,
   `Parent`), `internal/server/work.go`, `internal/server/graph.go`. Ready
   and Claim keep requiring exactly one project for now (`ErrOneProject`
   unchanged) — cross-project ordering is step 2, not this one. `kinds`
   matches any (OR, `n.kind = ANY($n::text[])`); `any_labels` matches any
   (OR, `n.labels && $n::text[]`); `labels` stays AND (`@>`, unchanged);
   `parent` filters `n.parent_id = $n`, resolved the way
   `NodeListQuery.Parent` already is. `status`/`held` are rejected by the

   `ReadyRequest` — reads only, as the work order states.
   *Proof:* `go build ./...`; `internal/domain/ready_test.go` and the

   `ListNodes`-with-`any_labels` acceptance criterion is proven.

2. **Cross-project round-robin for `Claim`/`ClaimNext` and `Ready`.**
   New migration `internal/store/migrations/00019_claim_cursors.sql`:
   table `claim_cursors(org_id, principal_id, filter_hash, project_id,
   updated_at)`, primary key `(org_id, principal_id, filter_hash)`, FK on
   `org_id`. New `internal/store/queries/claim_cursors.sql` (`GetClaimCursor`,
   `UpsertClaimCursor`), regenerated via `sqlc generate`. In
   `internal/domain/lease.go`: `ErrOneProject`'s single-project requirement
   is dropped from `Claim`/`ClaimNext`'s path (it still applies to a
   direct `Ready` call with more than... no — see below); add
   `eligibleProjects(ctx, tx, orgID string, q ReadyQuery) ([]string,
   error)` — a plain `SELECT DISTINCT n.project_id FROM nodes n WHERE
   <readyWhere + filter predicates minus the project restriction>`,
   scoped to `q.Projects` when given, to every project of the org when
   not. Add `nextProject(last *string, eligible []string) string` — a
   pure function, unit-tested on its own: eligible sorted ascending by
   project id (ULIDs, so this is also creation order), cyclic-next after
   `last`, first element when `last` is nil or no longer eligible.
   `claimOnce` (`lease.go:235`): resolve `req.Projects` (already-plural)
   to the eligible set, compute a `filterHash` over the scope-defining
   fields only (`Projects, Kinds, Labels, AnyLabels, AssigneeKind,
   MinPriority, Parent` — not `Wait/TTL/Harness/AgentRef/SessionRef`,
   mirroring how `requestHash` already strips `Wait`), read the cursor row
   for `(orgID, actor.PrincipalID, filterHash)`, pick the project via
   `nextProject`, then call the existing `lockNextReady` with
   `Projects: [chosen]` exactly as today. On a successful claim (lease
   created, inside the same transaction), upsert the cursor to the chosen
   project; on a lost race (`errClaimLost`, `isLiveLeaseConflict`) the
   cursor is not advanced for that attempt — the outer retry in `Claim`
   recomputes eligibility and the cursor fresh. `Service.Ready`
   (`service.go:204`): drop the `project == ""` requirement (`currentProject`-style,
   org-wide when empty); resolve the eligible project set the same way;
   read (never write) the cursor to pick a starting rotation point; run
   the existing per-project ordered `Ready` query once per eligible
   project (bounded), interleave the pages round-robin starting from that
   point, and cap at the page size. `held_count` on an empty first page
   sums `HeldCount` (`hold.go:97`) over every project in the *requested*
   scope (not just the eligible-and-empty set, which by definition is
   empty) — call it once per scoped project and sum in Go rather than
   writing a new multi-project SQL aggregate.
   *Proof:* db-labeled ginkgo specs (`internal/domain/lease_test.go` or
   `ready_test.go`, whichever holds the existing `Claim`/`Ready` specs):
   two projects each carrying one ready node, `ClaimNext` with an empty
   filter twice returns one node from each project on the two consecutive
   claims (the literal acceptance criterion); `projects: [a]` claims only
   from `a`; `Ready` with no project lists both projects' nodes in the
   same turn order a matching sequence of claims would produce; an empty
   `Ready` page's `held_count` sums correctly across two held projects.
   Also a plain unit test for `nextProject` covering: no cursor, cursor on
   a project no longer eligible, cursor mid-cycle, single eligible
   project.

## Risks

- **The `FOR UPDATE` / window-function conflict was a real risk in the naive design and is designed around, not solved by fighting Postgres.** By keeping `lockNextReady` untouched and single-project, and doing project *selection* as a separate, unlocked, pre-step, there's no query that mixes `FOR UPDATE` with `DISTINCT`/windowing. If implementation finds a case where this still doesn't hold (e.g. some future combination), the fallback is a per-candidate-project retry loop (try to lock project A's top row; if nothing lockable, try B) — more round trips, same correctness. Worth an early spike in step 2 before committing to the query shape.
- **Concurrent claims by the same principal+filter can read the same stale cursor and both pick the same "next" project.** This degrades fairness (one claim "wastes" its turn) but never breaks correctness: the actual node lock is still `FOR UPDATE ... SKIP LOCKED`, so two claimants never take the same node. Accepted as a bounded-imprecision race, not fixed with a cursor-row lock, to avoid serializing unrelated claims on an unrelated project's contention.
- **`claim_cursors` cardinality is unbounded in principle** — `filter_hash` varies with `Kinds`/`Labels`/`AnyLabels`/`MinPriority`/`Parent`, so a caller that varies its filter per call grows the table forever. No sweep job for this exists in the repo today (the same is true of `idempotency_keys`, which has a `created_at` index laid down for a sweep that isn't implemented here either — see `internal/store/migrations/00013_idempotency_keys.sql`). This plan follows that existing precedent rather than inventing new retention machinery; if it's a problem in practice it's the same problem `idempotency_keys` already has, one level up.
- **`properties_test.go`'s `recomputeReady`** models the ready set from scratch for property-based comparison against the real query; it's unclear from this plan alone whether it needs updating to understand round-robin ordering or only the (order-independent) *set* of ready nodes, which wouldn't change. Flagged for the implementer to check at step 2, not resolved here.
- **mill's existing worker breaking at its first claim** (the fifth acceptance criterion) isn't something this repository's test suite can directly assert — it's a statement about a different repository's client code failing to compile/marshal once `project` no longer exists on the wire. Step 5's `buf breaking` check is the closest verifiable proxy available here; the actual criterion is proven by mill's own blocked node, not this one.

## Decisions

- **Cursor-backed rotation over lease-history-derived rotation** (see *Approach*): the work order's "per filter" requirement can't be satisfied without recording which filter a claim used, and leases don't carry that.
- **Round-robin implemented as project selection + the unchanged single-project locked query**, not a rewritten multi-project ordered SQL query, to stay compatible with Postgres's `FOR UPDATE` restrictions and to keep the change to `lockNextReady` at zero.
- **`status` and `held` on `NodeFilter` are rejected by the server, not silently ignored, when set on `ClaimNextRequest`/`ReadyRequest`** — the work order marks them "reads only"; an error is more legible than a filter field that quietly does nothing on two of the three RPCs that carry it.
- **No separate `docs/api.md` exists in this repository**; the proto file's own comments are the contract documentation the work order's "or wherever" resolves to. Only `docs/domain-model.md` gets an edit.
- **The existing root-level `-p`/`--project` is made repeatable and stays the one flag**, used both for bare-reference resolution (still exactly one value, or a clear error above one) and as `ready`/`claim`/`list`'s scope filter (zero, one, or many). A second, command-local `--project` on those three commands was tried and rejected: it breaks `-p`'s shorthand via cobra/pflag's flag-set merge and fails the existing `mcp_test.go:1294` spec, confirmed by running it (see Steps §3).
- **`HeldCount` is summed in Go across scoped projects rather than given a new multi-project SQL form**, consistent with keeping this change's SQL surface as small as the work order's ordering requirement actually demands.
- **Canonical project order for the rotation is ascending `project_id`** (ULIDs, so this is also project-creation order) — arbitrary but deterministic and needs no extra lookup, since every row already carries it.
