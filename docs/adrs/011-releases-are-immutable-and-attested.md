# A release is a tag: built by goreleaser, published by the workflow, immutable, attested, and described by a packslip

## Context and Problem Statement

Skift has never been released. There are no tags and no GitHub releases, and no workflow runs on a tag. The `Makefile` already derives a semver from `git describe --match 'v*'`, and [publish.yml](../../.github/workflows/publish.yml) pushes an image to GHCR on every push to `main`, tagged by commit and never by version. Anyone who wants skift builds it from a checkout or pulls a moving tag that nothing lets them verify.

A release is the first thing skift hands to someone who does not trust its author. What does a release consist of, who builds each part of it, and what lets a stranger check that what they downloaded is what this repository built?

## Decision Drivers

- A consumer must be able to verify an artifact without trusting the maintainer: which workflow built it, from which commit, containing what
- No long-lived signing key or model credential lives in CI; identity comes from the workflow run itself
- A published release never changes, so every part of it must exist before it is published
- Installing skift is one command that verifies, and it works on every platform skift is released for
- The version is computed in one place; a development build, a rehearsal and a release cannot disagree about it
- A release can be rehearsed on a laptop: the build is a `make` target, not something only CI can do
- Each job holds only the permissions its work needs
- This is the first repository of several that will release the same way, so it uses the builder they will share

## Considered Options

1. Hand-written recipes in the Makefile for every artifact, published by a workflow
2. goreleaser end to end: build, release, image and publish in one `goreleaser release`
3. goreleaser as the builder behind a `make` target, with the workflow publishing

## Decision Outcome

Chosen option: **goreleaser builds, the Makefile is the door, and the workflow publishes**, because it gives the build a maintained implementation while keeping the order of publication and the permissions of each step in the repository's own hands.

The decision has nine parts. The pipeline they describe is built in two steps, binaries first and then the image, the compose file and the notes; this record describes the whole.

### 1. Trigger and version

A pushed tag matching `v<semver>` is the only event that makes a release. The version is the tag without its `v`, and the Makefile computes it. A tag with a semver prerelease part, such as `v0.2.0-rc.1`, publishes a GitHub prerelease. A person chooses the version and pushes the tag.

Rejected: release-plz or semantic-release choosing the version from commit history. They automate a decision made a few times a year, and add a bot with write access to do it.

### 2. Who builds and who publishes

`make release` runs [goreleaser](https://goreleaser.com) with publishing skipped. It compiles `skift` for linux/amd64, linux/arm64 and darwin/arm64 with `CGO_ENABLED=0` and `-trimpath`, archives each, has syft catalogue it, and checksums the result. The build is reproducible: an archive's bytes depend only on the commit, so anyone can rebuild a tag and compare digests. The Makefile computes `VERSION` and goreleaser stamps it. The image is assembled from the linux binaries goreleaser built, not compiled a second time.

Creating the release, pushing the image, signing, attesting and tagging belong to the workflow. `make build`, `make package` and `publish.yml` keep the Makefile's own `go build`.

Rejected: hand-written tar, syft and checksum recipes. They would be ours to maintain, and so would every later format: deb, Arch, Homebrew.

Rejected: goreleaser end to end. Its publishing runs in one job that holds every write permission, pushes image tags before the release exists, and shows the image's digest only to a hook.

### 3. Release assets and their names

A release carries exactly these:

| Asset | What it is |
|---|---|
| `skift_<version>_<os>_<arch>.tar.gz` | `skift`, `README.md` and the ISC `LICENSE.md`; owner 0:0, every mtime the tagged commit's time. One per platform |
| `skift_<version>_<os>_<arch>.cdx.json` | The archive's CycloneDX JSON SBOM, generated by syft. One per platform |
| `SHA256SUMS` | sha256 of every other asset but the packslip, in `sha256sum` format |
| `packslip.sigstore.json` | The signed manifest describing the release |
| `docker-compose.yaml` | The compose file, pinned to this release's image |

`<os>_<arch>` is `linux_amd64`, `linux_arm64` or `darwin_arm64`.

Rejected: platform names in another convention, such as Rust target triples. The names above are what Go tooling produces and what installers that pick an asset by platform already recognise.

### 4. Signing

[GitHub artifact attestations](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations) sign each archive and the image, once for build provenance and once for the SBOM. A [packslip](https://packslip.dev) manifest, signed with the release workflow's identity, describes the release for installers.

[mise](https://mise.jdx.dev) is the install path skift documents first: `mise use packslip:github.com/steading-ai/skift` verifies the manifest and pins its signer. The same manifest declares skift's agent skills, the directories under `plugin/skift/skills/`, so that `mise skills sync` links the skill matching the installed binary into an agent's skills directory. Asset names stay platform-conventional so that mise's `github:` backend also selects the right archive unaided. Every release is installed both ways, on every platform, before its run is green.

Nothing else signs.

Rejected: `cosign sign-blob` beside the attestations. It is a second signature format that no consumer of a skift release reads.

Rejected: a GPG-signed `SHA256SUMS`. It needs a long-lived key in CI and proves less than an attestation, which names the workflow and the commit.

### 5. Immutability

[Immutable releases](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/immutable-releases) are enabled on the repository. Every asset is uploaded to a draft, the draft is published once it is complete, and only the title and the notes change afterwards. A version that fails after publication is spent; the fix is the next version.

Rejected: publishing first and attaching assets as they are ready. An immutable release refuses them, and a mutable one is a release whose contents depend on when it was downloaded.

### 6. The image

`ghcr.io/steading-ai/skift` is a multi-arch image for linux/amd64 and linux/arm64, built from the binaries inside the archives. It is pushed by digest and attested in the registry before the release is drafted, and tagged only after the release is published.

`X.Y.Z` is never moved: the workflow refuses to overwrite it. A stable release also moves `X.Y`, `X` from 1.0 on, and `latest`, each only forward, so a patch to an older line never takes `latest`. A prerelease gets its exact tag alone. A digest pin is the immutable reference. `publish.yml`'s `main` and commit tags continue as the edge feed.

The image stays `scratch`. The binary embeds fallback CA roots from `golang.org/x/crypto/x509roots/fallback`, which Go consults only where the system has none, and runs as uid and gid 65532.

Rejected: exact-version tags only. It breaks what image consumers expect, and a digest pin already gives immutability to whoever wants it.

Rejected: a bare `0` tag during 0.x. A minor bump may break, and a major tag would promise it does not.

Rejected: a distroless base, or a distro build stage, for the sake of CA roots. Either is another input to track and attest for one file.

Rejected: relying on the roots tailscale bakes in. They cover Tailscale's control plane and nothing else.

### 7. Compose

`contrib/docker-compose.yaml` runs PostgreSQL and `skift serve` with the Tailscale transport configured. Tailscale is the only network transport skift has today; that it appears there is a property of the compose file, and other transports join it as they exist. The release carries a copy rendered with the image as `X.Y.Z@sha256:<digest>`, the form Renovate's docker managers update as a pair.

Rejected: bind-mounting the unix socket to the host. Skift identifies socket callers by the `SO_PEERCRED` uid, and a uid seen across a user namespace is the container's view of it: rootless podman maps the host user to 0, and Docker Desktop's VM passes no socket out at all. The identity would be wrong or absent, silently.

### 8. Release notes

[communiqué](https://communique.jdx.dev) writes the notes after publication, in its own workflow. It authenticates to its model provider by [workload identity federation](https://platform.claude.com/docs/en/manage-claude/workload-identity-federation): the job exchanges its GitHub OIDC token for a short-lived access token, and the repository stores no model credential. A failure there does not unpublish anything; the release keeps the notes GitHub generated.

Rejected: notes before publication. It puts a model call on the critical path of an immutable artifact, for text that stays editable.

Rejected: GitHub's generated notes alone. They list merged pull requests, and most of skift's history is direct commits.

Rejected: an API key in a repository or environment secret. A long-lived credential in CI is what the rest of this record avoids.

### 9. Hygiene

Every action is pinned by commit in `.github/workflows/actions.lock`. `make lint` runs [jactionlint](https://jactionlint.jdx.dev) over the workflows. Each job declares the least permission its work needs, and `contents: write` appears only in the jobs that create, publish or annotate the release. Renovate manages everything the repository pins, Go modules, mise tools, image digests and actions alike, because a released binary embeds its dependencies, its CA roots among them.

Rejected: bumping dependencies by hand. That is how a distrusted CA or a vulnerable module stays in a released binary until someone happens to notice.

### Out of scope

Package repositories; deb, Arch and Homebrew packages; notarization of the darwin binary; and a reusable workflow shared across repositories. Each waits on something this record does not decide.

### Consequences

- **Good**: A stranger can check an archive or the image against the workflow and commit that built it, with `gh attestation verify` or by installing through mise, and can rebuild a tag to compare digests.
- **Good**: CI holds no signing key and no model credential.
- **Good**: A release is rehearsed with `make release` and proved by a release candidate tag before the version people will install.
- **Good**: deb, Arch and Homebrew are goreleaser configuration when their time comes.
- **Bad**: The link-time version stamp is written twice, in the Makefile and in goreleaser's configuration. A spec holds them together.
- **Bad**: A release that fails after publication cannot be repaired, only superseded.
- **Bad**: The embedded CA roots move only when `golang.org/x/crypto` does, so a CA distrust needs a dependency bump and a release.
- **Neutral**: The edge image built on every push to `main` is not attested. Only releases are.

## Rejected Options

### Hand-written recipes in the Makefile

One place for the version and no new tool. Rejected because the reproducible archive, the SBOM and the checksum file would each be shell this repository maintains alone, and each package format added later would be more of it.

### goreleaser end to end

One command and one configuration file. Rejected because the order of publication is the security property: the image must be attested before the release names its digest, the release must be complete before it is published, and tags must follow publication. `goreleaser release` does these in its own order, in one job with every write permission, and splitting its phases across jobs is not available in its open-source edition.
